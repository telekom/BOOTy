# Changelog

All notable changes to BOOTy are documented here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and BOOTy uses
[Semantic Versioning](https://semver.org/). The newest release is at the top.
Release sections are generated from the pull request titles and the notes in
[changes/](changes/README.md); [CONTRIBUTING.md](CONTRIBUTING.md#changelog)
describes how. Do not edit this file in a pull request.

Each line names its pull request. Lines without a number are commits that were
pushed without a pull request. Tags without a GitHub release are marked
"tag only". The `main` history was rewritten before `v0.1.0`, so the `v0.0.x`
tags are not ancestors of `main`; their entries come from the GitHub release
notes and the history of each tag.

## [Unreleased]

## [0.2.0-rc.17] - 2026-10-22

### Highlights

- Check supported manifests daily with GitHub Dependabot only. Tool literals,
  inline images, source refs, Debian EFI packages, maintained forks, checksums
  and compatibility fixtures require coordinated manual review.
- Make vulnerability findings advisory with visible scan warnings and
  current-head PR reports; keep build, test and lint failures blocking.

### CI, build and tests

- track supplemental dependencies and report security findings
- verify mixed-case annotation tags are escaped
- track curated Go fork replacements behind approval
- keep updates native to GitHub Dependabot

## [0.2.0-rc.16] - 2026-10-21

Changes merged after `v0.2.0-rc.15`. Without `CAPRF_LEGACY_COMPAT` and without
the new keys, only the items under "Behaviour changes in all modes" change
behaviour.

### Highlights

- `CAPRF_LEGACY_COMPAT=true` makes BOOTy behave like the CAPRF legacy shell
  provisioner (power off, wait on failure, disk selection and wipe, GRUB drop-in,
  provisioner files in the ramdisk, transport rules, network wait, hostname, NIC
  firmware log, Mellanox VFs, grow target).
- `CAPRF_LEGACY_COMPAT` is a preset: some legacy behaviours also have their own
  native option, and an explicit option always wins over the preset (#648).
- New deprovision mode `MODE=decommission` (CAPRF `force-clean`) (#586).
- EVPN: the L3VNI provisioning network advertises Type-5 routes only, and every
  host gets its own router MAC (#582, #583).
- `make check-iso` builds `booty-check.iso`, one generic ISO for the bm4x
  cable check (#727): links mode (IPv6 link-local only), the bm4x-cablecheck
  LLDP identity on every NIC, a wait of up to 90 s for the LLDP neighbors, the
  health and cabling checks (`CHECK_PROFILES=health,cabling`, #731), and
  `CHECK_HOLD=until-poweroff`. It boots with BIOS and UEFI, also with Secure
  Boot.

### Behaviour changes in all modes

- An image whose format probe fails with a transient error (timeout,
  connection refused) no longer goes on to the disk wipe: BOOTy retries
  the probe twice and then stops before the wipe with `BOOTY-IMG-004`.
  Before, a qcow2 image on a ramdisk without `qemu-img` could wipe the
  disk and fail afterwards (#789).
- BOOTy stops the network before it leaves the ramdisk (#723): after the log
  lines are shipped, GoBGP sends a BGP Cease to every peer and BFD sends
  AdminDown, bounded to 5 s, then BOOTy kexecs, reboots or powers off. This
  covers the provision handoff, the power off after a deprovision (like the
  legacy `shutdown now`, which stops FRR), a reboot command, a failed run,
  an unknown mode and the token failure reboot. The switch ends the session
  at once instead of after the BFD detection time or the hold timer. The
  rescue shell keeps the network. When the reboot or power off fails after
  the stop, BOOTy sets the network up again to report the error; a failed
  `kexec -e` falls back to the reboot.
- When a provision uses one named disk (`DISK_DEVICE` or
  `DISK_SERIAL_NUMBER`, without `WIPE_ALL_DISKS` or explicit RAID), the
  block device settle wait counts from boot: BOOTy watches `/sys/block`
  from the module load on, so disks that settled while the network came
  up no longer cost another 2 s. Every other provision and every
  deprovision still observes the full 2 s window, because an HBA with an
  asynchronous SCSI scan can present disks late (#762).
- GRUB on the UEFI ISO path no longer shows its menu for 1 s: it has
  `timeout_style=hidden` and `timeout=0` and boots at once. This saves the
  1 s wait and about 7.4 KB of menu drawing on the serial console (about
  0.65 s at 115200 baud) per UEFI boot. Esc or Shift held while GRUB starts
  opens the menu (README, "ISO boot paths"). ISOLINUX (BIOS) already
  booted at once (#778).
- The `ERROR_URL` body of a failed provision or deprovision step now carries a
  stable failure code: `step <name> failed [BOOTY-<AREA>-<NNN>]: <error>`.
  [docs/failure-codes.md](docs/failure-codes.md) lists the codes (#706).
- The ramdisk is built from Debian 13 trixie instead of 12 bookworm and runs
  the Debian-signed Linux 6.12 LTS kernel instead of 6.1. The default and
  gobgp initramfs are about 6 MB smaller, slim about 3.4 MB larger (newer
  kernel modules and the added NIC drivers), the kernel about 4 MB larger. The opt-in
  `KERNEL_SUITE=trixie-backports` build argument selects Linux 7.x; do not use
  it with RAID or `DISK_MIRRORING_MODE`, because target OS kernels up to 6.18
  cannot assemble md arrays created on 6.19 or later (#701).
- The default and gobgp initramfs ship `sg_sanitize` and `sg_format`
  (sg3-utils) and all flavors the `sg` module, for the SAS secure erase (#701).
- The initramfs ships the VF drivers `igbvf` and `ixgbevf` and the NIC drivers
  `qede`, `cxgb4`, `sfc` and `ionic` (#701).
- The network setup waits up to `NIC_WAIT_SECONDS` (default 30, YAML
  `network.nicWaitSeconds`) for configured NICs that do not exist yet, and
  repeats netlink dumps that the kernel interrupted because links changed
  meanwhile (`NLM_F_DUMP_INTR`). Before, a NIC that appeared a moment after
  start could end the run at once.
- Provisioning and hard deprovision zero the superblock of every
  `linux_raid_member` (whole disks and partitions) on the disks they wipe,
  after `stop-raid` stopped the arrays: provisioning on the target and mirror
  disk, or on every disk with `WIPE_ALL_DISKS=true`; hard deprovision on the
  device override and its mirror companion, else on every disk. The new
  `RAID_SUPERBLOCK_CLEAR=all` (preset by `CAPRF_LEGACY_COMPAT`) zeroes them on
  every disk of the host in `stop-raid`, like `clear_mdadm_superblocks` of the
  CAPRF provisioner (#581).
- GoBGP mode with `frr.conf` neighbors: the vars `BGP_PEER_MODE`,
  `BGP_INTERFACES`, `BGP_NEIGHBORS`, `BGP_REMOTE_ASN`, `BGP_KEEPALIVE` and
  `BGP_HOLD` no longer apply (each session takes its own values or the
  `frr defaults` profile). BOOTy logs a warning for each one that is set.
  Statements that are parsed but not applied yet (`allowas-in`, `route-map`,
  `soft-reconfiguration inbound`, `bgp ebgp-requires-policy`,
  `bgp suppress-duplicates`, `bgp bestpath as-path multipath-relax`) are
  logged too (#643).
- A provisioner netplan route with `from`, `table`, `metric` or `scope` now
  fails the network setup (with `NETPLAN_STRICT=false` it is dropped with a
  warning). BOOTy does not apply these keys; before, the `via` of a `from:`
  default route became the static gateway (#642).
- The provisioner `frr.conf` is read with a block parser that follows FRR's
  reading rules. A statement that BOOTy does not implement, or an unknown netplan
  key, now fails the network setup and the run. `FRR_CONFIG_STRICT=false` and
  `NETPLAN_STRICT=false` log and skip them instead (invalid values,
  unsupported block openers and netplan route keys such as `table` still
  fail). Statements without effect on
  routing (`neighbor X description`, `bgp log-neighbor-changes`, netplan
  `optional`) pass in both modes (#642).
- A failed `TOKEN_URL` renewal no longer reboots at once: BOOTy stops the
  active task, reports `token renewal failed, task stopped: <reason>` to
  `ERROR_URL`, then reboots (or waits with `FAILURE_ACTION=wait`). The
  renewal attempts also stop when the token expires (#680)
- Netplan `set-name` renames the single NIC that its `match` selects, and a glob
  or MAC `match` selects the NIC of a static address, like `netplan apply`.
  Before, BOOTy ignored `set-name` and used the first NIC (#641).
- Disk wipes are thorough: before the partition table, BOOTy stops LVM,
  dm-crypt and MD devices on the disk, removes PV labels and MD superblocks,
  wipes the signatures and the first and last MiB of every partition, then the
  disk edges, and runs `blkdiscard` where supported. A restored old partition
  table finds nothing. `WIPE_DEPTH=quick` (preset by `CAPRF_LEGACY_COMPAT`)
  keeps the old disk-only wipe (#667)
- A provisioner netplan file or `frr.conf` that exists but does not parse
  (malformed YAML, invalid values such as an out-of-range ASN) now fails the
  network setup and the run. Before, BOOTy fell back to the vars. Unknown YAML
  keys still pass. `frr.conf` is read only when netplan files are present (#636).
- FRR config lines without indentation are now read. Numbered peers keep their
  own `remote-as`; a `frr.conf` with different numbered `remote-as` values or
  with `remote-as external` is a parse error and so fails the run (#634, #636).
- EVPN: `advertise-all-vni` enables L2 EVPN (Type-2/Type-3) only when the
  provisioning VNI is not an L3VNI. The CAPRF `frr.conf` (L3VNI 1000) now gives
  Type-5 routes only (#582).
- EVPN router MAC and provision bridge MAC: netplan `macaddress` of the provision
  bridge, else `02:54` + last 4 bytes of the IPMI MAC, else `02:54` + the 4 bytes
  of the underlay IPv4. The shared fallback `02:54:00:00:00:01` is gone. A
  non-IPv4 underlay is an error (#583).
- IPMI NIC autodetection no longer falls back to the first addressed NIC. Hosts
  without an IPMI NIC now derive the router MAC from the underlay IP (#592).
- Image source probing uses `GET` with `Range: bytes=0-0` instead of `HEAD`, so
  presigned URLs work. Every status `>= 400` rules a source out (#599).
- HTTP image downloads abort after 2 minutes without data and go through the
  normal retry and wipe-on-error path (#637).
- DHCP sends the default parameter request list (option 55), so servers such as
  Kea return router, DNS and MTU (#598).
- `e2fsck` killed or canceled now fails `check-filesystem` (#604).
- Soft deprovision without `grub.cfg` now fails instead of reporting success. A
  new `release-stale-mounts` step unmounts the target before rescue retries (#635).
- Ambiguous unnamed Linux root partitions are probed by content like the legacy
  script, instead of failing (#601).
- A separate `/boot` partition from the image fstab is mounted, so `update-grub`
  writes the `grub.cfg` that the firmware boots (#595).
- `EXTRA_KERNEL_PARAMS` from the vars file is appended to
  `MACHINE_EXTRA_KERNEL_PARAMS` (#594).
- Machine files: symlinks are recreated as links, files below `dev`, `proc`,
  `sys`, `run` are skipped, and mountpoints with a symlink in the path are
  refused (#629).
- The CAPRF client and `network.NewHTTPClient` use `http.ProxyFromEnvironment`
  (#589).
- Filesystem resize runs only the tool for the detected filesystem (#639).
- `sync()` runs before kexec, reboot and power off (#597, #623, #585).
- Before the target chroot, BOOTy creates the `/dev/disk/by-uuid`,
  `by-partuuid`, `by-label` and `by-partlabel` links, so `update-grub` writes
  `root=UUID=` instead of `root=/dev/sdXN`. `DISK_LINKS=false` turns it off
  (#671).
- `IMAGE_CHECKSUM` is compared with the file as downloaded (for example the
  `.lz4` file of a published `image.raw.lz4.sha256`), like the CAPRF legacy
  provisioner. `IMAGE_CHECKSUM_SCOPE=decompressed` keeps the old check of the
  decompressed image (#664). Upgrade: a config whose `IMAGE_CHECKSUM` is the
  digest of the decompressed image (or of the converted qcow2) must set
  `IMAGE_CHECKSUM_SCOPE=decompressed`, else the run fails with "checksum
  mismatch". For `oci://` sources nothing changes: both scopes hash the
  uncompressed layer.
- Before kexec, BOOTy unmounts the target filesystems (a busy block device
  mount is remounted read-only), so the installed OS does not replay the ext4
  journal of `/` or `/boot`. If `/proc/mounts` can not be read, BOOTy logs a
  warning. `KEXEC_UNMOUNT_TARGET=false` turns it off (#672, #678).
- When the netplan files, `frr.conf` or vars name an interface that does not
  exist (for example `enp1s0` while the ramdisk calls the NIC `eth0`), BOOTy
  renames the link that has this systemd predictable name (naming scheme v255).
  `PREDICTABLE_NIC_NAMES=false` turns it off (#673). ARI functions keep their
  slot in the path name (`enp65s1f8`), and a slotted bridge names a
  multifunction NIC behind it, like systemd v255 (#683).
- The default, gobgp and slim initramfs ship the NVMe, AHCI, MegaRAID, mpt3sas,
  SmartPQI and HPSA storage drivers, software RAID (`md_mod`, `raid0/1/10`,
  `raid456`), `loop`, `8021q` and `efivarfs` modules. Before, only virtio disks
  were visible on the Debian kernel. `efivarfs` is not loaded on BIOS systems.
  The default flavor's busybox applets (`sh`, `sync`, `blockdev`, `setsid`)
  work again; their links pointed into the build directory. Before the target
  disk selection and a wipe of all disks, BOOTy waits until the set of disks is
  stable for 2 seconds and the configured `DISK_DEVICE` or `DISK_SERIAL_NUMBER`
  exists, at most `DISK_SETTLE_TIMEOUT_SEC` (default 30, max 600, `0` turns it
  off). A `DISK_DEVICE` below `/dev/disk/` (by-id, by-path) now fails at once:
  the ramdisk has no udev to create these links; a `PARTITION_LAYOUT` device
  below `/dev/disk/` is used as it is, without a wait for the path. A serial
  number error that waiting can not fix (several disks with the serial, a disk
  below `MIN_DISK_SIZE_GB`, also when only `lsblk` sees the serial) ends the
  wait at once. A disk that reports 0 sectors is not there yet, not too
  small. Automatic disk selection skips a disk with 0 sectors (the
  legacy-compatible selection still takes it) (#670, #684).
- On a system booted via UEFI, a failure to mount efivarfs, to create the EFI
  boot entry or to remove the managed EFI boot entries now fails provisioning or
  deprovisioning, like the legacy scripts. Before, BOOTy logged a warning and
  reported success. `EFI_BOOT_ENTRY_REQUIRED=false` turns only "EFI variables
  unavailable" failures into warnings: efivarfs can not be mounted
  (`efi=noruntime`, `noefi`, a ramdisk without `efivarfs.ko`), `efibootmgr` is
  missing or can not read the variables, or the firmware refuses to delete an
  entry (a locked boot order on Lenovo XCC, HPE iLO, Dell iDRAC). A failed
  `efibootmgr -c` or a missing EFI loader always fails the run, also when the
  firmware refuses the new entry. Deprovisioning removes the entries before it
  wipes a disk. In a container BOOTy skips the EFI steps. `MODE=decommission`
  stays best effort. The slim flavor now ships `efibootmgr` (#669).
- `SECURE_ERASE=true` (and the YAML `deprovision.secureErase`) no longer
  falls back to a signature wipe on its own. A failed erase, a security-frozen
  or unsupported drive, a disk without an erase method and a missing erase tool
  fail the run with the reason. The new `SECURE_ERASE_FALLBACK=wipe` allows the
  wipe, logs it at `WARN` and names the disk in the success status. The method
  follows the media type: `nvme format` for NVMe, `hdparm` only for ATA disks
  (sysfs vendor `ATA`), `sg_sanitize` or `sg_format` for SAS disks, which took
  the `hdparm` path before. The ATA frozen check no longer reads `not frozen`
  as frozen. The plain wipe and `CAPRF_LEGACY_COMPAT` do not change (#704)
- `LOG_URL`: when CAPRF is slow or down, BOOTy drops `DEBUG` and `INFO` lines
  first and keeps `WARN` and `ERROR` (at most 8192 lines and 4 MiB queued), and
  posts one `BOOTY-LOG-001` line with the dropped lines per level when CAPRF
  answers again. Lines arrive in order. Tokens, passwords, JWTs, private keys
  and LUKS keys in a line are redacted before it is queued. Before kexec,
  reboot, power off or the rescue shell, BOOTy waits up to the new
  `LOG_FLUSH_TIMEOUT_SEC` (default 5, `0` to 60) for the queued lines to arrive
  (#711).
- BOOTy sets the clock before the first request that checks a TLS
  certificate: from `NTP_SERVERS`, the DHCP option 42 servers or the `Date`
  header of the CAPRF connectivity target, whose certificate chain is checked
  at the time it claims, within a window from the commit time of the build
  (`BOOTY_COMMIT_TIME`) to five years after it. It writes the RTC. A host with a wrong RTC now
  provisions over TLS without `SKIP_TLS_VERIFY`. `TIME_SYNC=off` keeps the old
  behaviour. A certificate that is not valid at the local clock now gives an
  error that names the skew (`BOOTY-TIM-002`) (#713).
- GoBGP mode starts a BGP peer again at once when its session ends and
  BOOTy did not stop it (the leaf ends the session, BFD down, hold timer).
  GoBGP held the peer 5 s in Idle and refused the leaf's connections
  (osrg/gobgp#3735); a `clear bgp` on the leaf took up to 36 s, now about
  as long as with FRR. Peers whose graceful restart routes GoBGP keeps
  stay as they are (#745).
- GoBGP mode runs GoBGP 4.10.0 (was 3.37.0). GoBGP 3.37.0 panicked on a
  truncated EVPN NLRI from any peer, also on an IPv4-only session, and that
  ended BOOTy (PID 1); 4.10.0 rejects the UPDATE (RFC 7606), and a test pins
  that for every EVPN route type. GoBGP sends the
  Extended Message capability (RFC 8654) like FRR, and its peer events appear
  in the BOOTy log (component `gobgp`). It retries a connection after 0.75 to 1
  times the connect retry timer and at least 2 s (was 1 to 2 times, at least
  1 s). A `local-as` session still rejects paths with the router AS, now
  through the BOOTy import policy. GoBGP comes from the fork tag
  `github.com/MaxRink/gobgp/v4` v4.10.0-booty.2: v4.10.0 with eight fixes,
  among them a session that lost carrier comes back after 1 s of Idle, not
  5 s (osrg/gobgp#3740), a connection collision no longer waits 5 s in Idle
  (osrg/gobgp#3741), and FRR's MAC/IP routes with the EVPN ARP/ND community
  are kept instead of being treated as withdrawn. `docs/networking.md` lists the fixes and when to
  drop the fork (#699).
- GoBGP mode sets the N bit (RFC 8538) of the graceful restart capability
  like FRR: on from `frr version` 8.3 (the CAPRF configs) and without
  `frr.conf`, off below 8.3 (the bm4x templates). New key
  `BGP_GRACEFUL_NOTIFICATION` (YAML `network.bgp.gracefulNotification`).
  `TestOpenCapabilitiesMatchFRR` compares the OPEN of GoBGP on the wire
  with FRR 10.2.1 and 10.3.1 captures (#744).
- BOOTy stops the firmware LLDP agent of Intel NICs (i40e `disable-fw-lldp`
  on, ice `fw-lldp-agent` off) by default in every mode and does not put it
  back; ice keeps the flag in the NVM, so the agent and its firmware DCBX stay
  off for the installed OS too. The agent consumes the switch's LLDP frames,
  so the switch never sees the host. The legacy ramdisk never touches the
  flag. `LLDP_DISABLE_FW_AGENT=false` (YAML
  `network.lldp.disableFirmwareAgent: false`) leaves it alone, and an SR-IOV
  profile that sets `firmware.fwLLDPAgent` owns the flag of its ports (#708).
- GoBGP mode originates its EVPN routes with FRR's route distinguisher
  `<router-id>:<n>` instead of `asn_server:provision_vni` on every host, and
  with MED 0 on the underlay `/32` and the Type-5 routes, like FRR. BFD
  advertises Required Min Echo RX 50 ms like FRR bfdd. New key `EVPN_RD`
  (YAML `network.evpn.rd`); `frr.conf` `rd` in the VRF's `address-family
  l2vpn evpn` is accepted (#710).
- GoBGP mode: a received EVPN Type-5 route that RFC 9136 says not to use is
  now treated as a withdraw of its route key, like FRR: an invalid or
  non-unicast router MAC, an ESI together with a gateway IP, or a zero label
  without a gateway IP. Before, BOOTy installed such routes (#747).
- DHCP mode runs a client on every physical NIC for the whole run, and every
  NIC keeps its own lease address plus a default route with metric 100 and
  `proto dhcp`, like systemd-networkd with the legacy netplan; before, the
  first lease won and the other NICs stayed without an address. Without a
  lease within 15 s the clients keep sending until the network is torn down
  (#750).
- DHCP mode: when a lease expires or the server answers DHCPNAK, BOOTy
  removes its address and default route, and after an expiry the client of
  the NIC starts over with a DHCPDISCOVER (RFC 2131). A lease without a
  lifetime or a server identifier is not applied, like systemd-networkd
  (#751).
- DHCP mode uses the DNS servers and domain (search) of the leases in
  resolv.conf and sets the lease MTU on the NIC, clamped like
  systemd-networkd (at least 576, 1280 with IPv6, at most the NIC maximum),
  like systemd-networkd and systemd-resolved in the legacy ramdisk (#753).
- BOOTy sends LLDP on the NICs that a netplan match block with
  `emit-lldp: true` selects (the legacy L2 netplan `all-en`, `all-eth`),
  and in every network mode, like systemd-networkd (a NIC that appears
  later too, except in GoBGP mode, whose underlay sends on the NICs of
  the setup); before, only the GoBGP underlay sent and took the
  block ID as an interface name (#756).
- BOOTy loads the kernel modules in dependency order (the `depends` and
  `softdep` fields of each module) and in parallel, instead of retrying
  failed loads up to five times: the module phase takes 0.9 s instead of
  2.5 s on a 4-CPU VM, and the kernel no longer prints about 500
  `Unknown symbol` lines (35 KB, about 3 s on a 115200 baud serial
  console). NIC drivers keep their former load order, so the NIC names do
  not change. One line `loaded kernel modules count=... modules="..."`
  replaces the line per module; a module that fails still logs a warning
  (#758).
- The LLDP receive finds its NICs in the background. With one NIC the NIC
  detection waits 3 s for more NICs, and the connectivity check waited for
  it: a single-NIC host reaches the network 3 s sooner. The inventory
  report still listens for neighbors for one transmit interval after the
  receive sockets open, and does not wait when no NIC was found (#760).
- GoBGP mode: in L3VNI (Type-5 only) mode a Type-5 route with another VNI
  is not installed, like FRR on a classic VXLAN device (RFC 8365). With an
  explicit `EVPN_TYPE5_ONLY=true` and a `provision_vni` that differs from
  the VNI of the fabric L3VNI, the fabric Type-5 routes are now dropped;
  set `provision_vni` to the L3VNI (#773).
- GoBGP mode compares `frr version` like FRR's `frr_version_cmp`, so the
  default N bit is now off for `frr version 8`, `8.3~rc1` and other versions
  below 8.3 that the old compare treated as the running FRR (#774).
- DHCP mode sends the DHCP options of systemd-networkd (client identifier,
  its parameter request list, maximum message size) and applies the
  classless static routes (option 121), the static routes (option 33) and
  the domain search list (option 119) like networkd; a 0.0.0.0 router no
  longer gives an on-link default route (#776).
- The published ISOs boot with `loglevel=4`: the console shows only kernel
  errors. On x86 this removes about 30 KB of kernel console output before
  BOOTy starts (about 2.6 s on a 115200 baud BMC serial console; 63.7 KB,
  5.5 s, together with the `Unknown symbol` lines that #758 removes).
  BOOTy logs the kernel's Secure Boot and lockdown messages in one line
  (`kernel security state`), adds `uptime` (seconds since the kernel start)
  to `starting BOOTy`, sends the whole kernel log once to `DEBUG_URL` when
  it is set (never to `LOG_URL`, whose lines CAPRF classifies), and puts
  the whole `dmesg` in the crash metadata. Log redaction also hides signed
  URL signatures (`X-Amz-Signature=`, `signature=`, `sig=`). ISOs that
  CAPRF builds itself need `loglevel=4` on their own kernel command line
  for the same gain (#777).
- With provisioner netplan files (the input of the legacy ramdisk), every
  physical NIC gets its predictable (udev) name, like in the legacy
  ramdisk, also those that the network config does not name: interface
  names in logs and the LLDP port IDs change from `eth0` to, for example,
  `enp1s0`. These extra renames are best effort and leave the NICs of netplan
  `set-name` alone. A NIC that appears after the network setup keeps its
  kernel name (#780).
- New failure codes for ramdisk payloads (docs/proposal-ramdisk-split.md):
  `BOOTY-PAY-001` when the vars need FRR and the ramdisk lacks it, and
  `BOOTY-PAY-002` when a payload archive is from another build. A split
  build lists the payloads it left out in `/etc/booty/payloads/split`; on
  such a ramdisk FRR mode without the FRR archive fails with
  `BOOTY-PAY-001` before the network setup or the FRR start. The default,
  gobgp and slim flavors have no split list and behave as before (#781).
- DHCP mode: a NIC that appears after the network setup (a late driver)
  gets a DHCP client too, like systemd-networkd (#788).
- DHCP mode has its own DHCPv4 client (`pkg/network/dhcp4`) instead of
  `github.com/digineo/go-dhclient`, which is GPL-3.0 and so could not be
  linked into the Apache-2.0 BOOTy binary. The client follows
  systemd-networkd: backoff 2 to 64 s, unicast renewal, broadcast rebind,
  rapid commit, INIT-REBOOT (called on carrier return, #793),
  DHCPRELEASE at stop, the reply checks of networkd. Replies with option
  overload (52) are dropped (#790).
- A payload manifest also carries `arch=`, and BOOTy refuses a payload of
  another architecture with `BOOTY-PAY-002` (#791).
- DHCP mode: a NIC whose carrier returns confirms its lease with an
  INIT-REBOOT request at once, like systemd-networkd. Unlike networkd the
  lease stays while the carrier is gone (it still ends at its expiry), so
  an image stream from its address resumes (#793).
- DHCP mode runs DHCPv6 on every DHCP NIC, started by the M or O flag of a
  router advertisement, with the messages of systemd-networkd; the leased
  address goes on the NIC as /128 and its DNS servers into resolv.conf
  (#795).
- GoBGP mode: a BFD reset of a BGP session sends Cease/BFD Down (subcode 10,
  RFC 9384) like FRR, instead of Cease/Administrative Reset (subcode 4). The
  peer logs the new reason (#811).
- GoBGP mode: new option `BGP_CONNECT_AT_ONCE` (YAML
  `network.bgp.connectAtOnce`), off by default: a peer connects at once when
  it leaves Idle, like FRR, instead of after a random 1.5 to 2 s. It is off
  because after a carrier loss GoBGP and the leaf then connect at the same
  time, and about one collision in ten still ended with a second session in
  the production template lab. Retries wait the connect timer, except after
  a connection that failed in OpenSent: then the next connect comes after
  1.5 to 2 s, whatever the timer is (#811).
- GoBGP mode: the OPEN message also has the Enhanced Route Refresh (RFC 7313)
  and Paths-Limit capabilities, like FRR (#811).
- GoBGP mode: GoBGP is pinned to the fork tag v4.10.0-booty.10. When BOOTy
  and the leaf connect at the same time, GoBGP keeps the connection that
  survives the collision instead of waiting 5 s in Idle. After a short
  carrier flap, a BFD reset shortens the running 5 s Idle hold to the 1 s
  idle hold after reset, so the leaf's connection is no longer refused
  (#811).
- GoBGP mode: after a carrier loss the session comes back once. GoBGP closes
  the leaf's losing connection of a collision only when the leaf's OPEN
  arrives on it; before, the leaf connected again and with graceful restart
  the session went down a second time. A NOTIFICATION from the leaf on its
  connection no longer holds the session 5 s in Idle (#811).
- The ramdisks no longer ship `lldpd` and `lldpcli`. BOOTy sends and
  receives LLDP itself; in the rescue shell, `booty lldp neighbors` shows
  the neighbor of each NIC (like `lldpcli show neighbors detail`) and
  `booty lldp status` what BOOTy sends (like `lldpcli show interfaces`),
  both with `--json` (#812).
- BOOTy no longer queries the NTP servers of the DHCP leases (option 42) by
  default, like the legacy ramdisk, which has no NTP client. Set
  `TIME_DHCP_NTP=true` (YAML `time.dhcpNTP`) to query them after
  `NTP_SERVERS` (#819).
- In DHCP mode a DNS lookup goes at once to the current server of every
  link (the configured servers, each NIC with a lease; with search
  domains only the NICs with one), and the first positive answer counts,
  like systemd-resolved (#819).
- DHCP mode adds a routing rule per NIC: packets from the lease address of
  a NIC use a table with the routes of that NIC (table 10000 plus the
  interface index, rule priority 10000). A connection keeps its NIC when
  the kernel moves the default route after a link flap. systemd-networkd
  in the legacy ramdisk has no such rules (#820).
- DHCPv6 (RFC 8415): the client requests from the ADVERTISE with the
  highest preference of the first SOLICIT timeout, reads late replies on
  the socket of the transaction, and answers NoBinding in a RENEW or
  REBIND REPLY with a REQUEST. An information refresh time of 0 counts
  as 600 s (#825).
- DHCP mode: when the link watch fails, the old netlink subscription is
  closed and the new one lists the links, so a NIC or carrier change whose
  event was lost is seen; a failed Setup stops the watch, and the close
  at Teardown or a message of another netlink sender logs no warning. An
  OFFER or ACK with the server identifier 0.0.0.0 is dropped, like
  networkd. The first router solicitation after a carrier return waits a
  random 0.5 s to 1 s (RFC 4861, sd-ndisc) (#825).
- LLDP for netplan match blocks: when the link watch fails, the old netlink
  subscription is closed and the matches are resolved again after the new
  one, so a NIC whose event was lost sends LLDP too (#826).
- GoBGP mode: GoBGP is pinned to the fork tag v4.10.0-booty.16. With
  `BGP_CONNECT_AT_ONCE=true`, a session that BOOTy and the leaf open at the
  same time after a carrier loss no longer waits 5 s in Idle: GoBGP keeps
  its own connection when the leaf keeps it (RFC 4271 section 6.8), and it
  does not connect again while the session goes on with the leaf's
  connection. `BGP_CONNECT_AT_ONCE` stays off by default. GoBGP also sends
  IPv4 VPN multicast routes and routes with an IPv4-mapped IPv6 next hop
  to a peer only when the peer has the extended next hop capability
  (RFC 8950) (#831).
- LLDP is decoded with a fork of github.com/gopacket/gopacket v1.7.4
  (was github.com/google/gopacket v1.1.19) that returns an error instead
  of panicking on short TLVs and checks the order of the mandatory TLVs.
  A malformed 802.1, 802.3 or LLDP-MED TLV now leaves the fields of its
  group empty; before, BOOTy skipped only the bad TLV. netlink v1.3.1 is
  replaced by a fork that closes the subscription socket after a receive
  error. See docs/dependency-forks.md (#833).
- DHCP mode encodes and decodes DHCPv4 and DHCPv6 messages with
  `github.com/insomniacslk/dhcp` (BSD-3-Clause, through the fork
  `MaxRink/dhcp`, see `docs/dependency-forks.md`); the clients and the
  bytes they send do not change. Replies are read like networkd 255: a
  DHCPv4 option whose length does not fit its type and a DHCPv6 DNS
  option whose length is not a multiple of 16 are ignored, a repeated
  option 119 counts with its last copy, a truncated DHCPv6 option drops
  the message, IA or address, a malformed DHCPv6 option 24 is ignored as
  a whole, and a search list (option 119) with chained compression
  pointers is read (#835).
- LLDP for netplan match blocks: the link watch logs no warning when the
  run ends, and a netlink message of another sender only at debug level
  (#836).
- The root partition can have a root type of the Discoverable Partitions
  Specification (x86-64 or arm64), as in the Ubuntu 26.04 cloud image.
  Before, BOOTy only accepted the Linux filesystem type, so it did not find
  the root partition of such an image, and `ROOT_PARTITION_NUMBER` or
  `ROOT_PARTITION_LABEL` rejected it as "non-Linux" (#842).
- With `DISK_MIRRORING_MODE=raid-1`, BOOTy also writes
  `/etc/dracut.conf.d/90-booty-mirror.conf` with `rd.md.uuid` for the
  mirror arrays. Images that use dracut (Ubuntu 26.04) otherwise build an
  initramfs that does not assemble the arrays, and the installed system
  waits for its root device forever (#842).
- In GoBGP mode, an unnumbered BGP session waits 1 s in Idle when the
  carrier of its uplink returns, and then connects after a random 1.5 to
  2 s. Before, it waited 5 s when BFD went down before the carrier, and
  it refused the leaf's connection in that time (#844).
- LLDP sending follows the carrier in every profile with the timing of
  systemd-networkd 249 (#845). BOOTy watches the carrier with netlink link
  updates. On a carrier gain the first frame goes out 0.8 s plus a random
  jitter of 0 to 400 ms later, then 3 more 0.8 s plus jitter apart, then
  one every 29.8 s plus jitter. Without carrier BOOTy sends nothing, no
  frame counts, and it sends no shutdown LLDPDU. Before, the default
  `networkd` profile kept sending into a link without carrier, so after
  the link came back the next frame went out only at the next 30 s tick,
  and the frames had no jitter. A missing or renamed NIC is logged once
  again.
- GoBGP mode sends the unnumbered RAs like zebra (FRR 10.2): each fabric
  NIC joins `ff02::2` and answers a Router Solicitation (RFC 4861 section
  6.2.6: a random delay of up to 0.5 s, at least 3 s after the last RA).
  The RAs start before the peer discovery with 5 RAs 1 s apart, then one
  every 10 s, always from the link-local address after DAD. When a NIC
  gets carrier back, 4 fast RAs start again 1 s later, also without
  `bgp fast-external-failover`. The relearner sends no RAs of its own, and
  the peer discovery no longer sends an echo request to `ff02::1` (#846).
- GoBGP mode uses the GoBGP fork tag v4.10.0-booty.21, which is upstream
  GoBGP master after 4.10.0 plus the fork patches (#847). After a session
  ends, GoBGP waits in Idle like FRR 10.2.1 of the legacy ramdisk
  (`v_start`) instead of a fixed 5 s: 1 s after a TCP close and after an
  administrative shutdown, doubled up to 120 s for a NOTIFICATION
  received in OpenConfirm or Established or sent for a message error,
  back to 1 s for a hold timer expiry and for a NOTIFICATION in OpenSent.
  A BFD reset still waits 1 s. A new connection from a helper-only
  graceful restart peer while the session is up no longer ends the
  session. `EnablePeer` and `DisablePeer` no longer lose a queued
  request or change anything for the current admin state. A peer
  without RFC 8950 extended next hop support still gets no IPv4 routes
  with an IPv6 next hop; this is upstream code now.
- GoBGP mode: a BFD Down with diag 3 (Neighbor Signaled Session Down) no
  longer resets a BGP session at once while the session is coming up
  (Connect to OpenConfirm, or Established in the same or the next second
  of its uptime). A route reflector with `update-source` re-keys its
  multihop BFD session then, and BOOTy reset the RR session at the start
  now and then. BOOTy checks again: once the session is Established, it
  resets the session if BFD is not Up within multiplier x 1 s of the
  Down. A path failure (other diags) resets as before (#849).
- An unnumbered peer that moves to the switch's link-local address takes
  only the route-maps and the `bgp ebgp-requires-policy` reject of its own
  session. Before, when two switches did not answer at setup, the moved
  peer also took the policy of the other port's session, which shared the
  placeholder address, and could exchange no routes (#850).
- Unnumbered BGP sessions on different NICs keep their own route-maps and
  `bgp ebgp-requires-policy` reject also when the switches use the same
  link-local address (for example `fe80::1` on every port), like the
  per-interface peers of FRR. Before, one port's reject applied to the
  other port too, and a session could be Established but exchange no
  routes. This lifts the last case where a moved peer could take another
  port's policy (#850). The GoBGP fork tag is now v4.10.0-booty.22 (#851).
- BOOTy opens its BFD receive sockets before the first IPv6 RA and before
  the BGP peers, like FRR bfdd. The leaf starts BFD on that RA, and its
  first BFD packet no longer gets ICMP port unreachable. In FRR mode the
  direct daemon start runs `bfdd` before `bgpd` (#852).
- DHCP replies that systemd-networkd 255 drops are dropped too: a DHCPv4
  message option (56) that is empty, has a NUL before its end or a byte
  over 127; a DHCPv6 reply with a second client or server identifier, a
  preference other than 1 byte, a status code under 2 bytes or other
  than success, or an information refresh time other than 4 bytes
  (#840).
- The default, gobgp and slim ramdisks no longer ship `curl` and its
  libraries (libcurl, Kerberos, LDAP, SASL, libssh2, nghttp2/3, brotli and,
  in slim, OpenSSL and GnuTLS). BOOTy never ran `curl`: it fetches images,
  CAPRF callbacks and tokens with Go's `net/http`. In the rescue shell use
  busybox `wget` (HTTP and HTTPS, `--header` for a bearer token). busybox
  `wget` does not verify TLS certificates: busybox 1.38 prints "TLS
  certificate validation not implemented" and connects to any server
  (#814).
- `WATCHDOG_IPMI_FALLBACK` sends the BMC watchdog commands (Set and Reset
  Watchdog Timer) over `/dev/ipmi0` in process, and the ramdisks no longer
  ship `ipmitool` or `libfreeipmi`. The `split` build has no
  `ipmitool.cpio.zst` payload any more: remove it from the initrd list of
  the boot loader. Only FRR is a payload now. The rescue shell has no
  `ipmitool`: read or change BMC settings over Redfish, the BMC web
  interface or `ipmitool -I lanplus` from another host (#816).
- BOOTy converts qcow2 images to raw in process and the ramdisks no longer
  ship `qemu-img`. qcow2 versions 2 and 3 work, with zlib or zstd compressed
  clusters, extended L2 entries and snapshots (the active state is written).
  Images with a backing file, an external data file or encryption fail as
  before. A truncated image (a table or cluster past the end of the file)
  and an image whose virtual size is larger than the target disk now fail
  before anything is written. The `split` build has no `qemu-img.cpio.zst`
  payload any more: remove it from the initrd list of the boot loader. A
  qcow2 image never needs a payload, so `BOOTY-PAY-001` covers only FRR.
  `qemu-img` is gone from the rescue shell too (#815).

### Features

- The `iso` and `gobgp-iso` ISOs boot on UEFI (CD, virtual media and USB)
  and with Secure Boot through Debian's shim and signed GRUB, besides BIOS.
  Under Secure Boot, in-band Mellanox SR-IOV configuration (`mstconfig`) and
  kexec into kernels not signed by Debian do not work (#737).
- The initramfs ships `inet_diag`, `tcp_diag` and `udp_diag` (#737).
- Out-of-band status: a fixed `BOOTY1 run=... phase=... code=... step=...
  result=...` line on every active console at each phase change and at the
  end of a run, also when the network setup fails (`OOB_STATUS`, default
  `serial`). The network failure report to `ERROR_URL` carries its failure code.
  A run that fails before a mode (vars file, network, token) now logs the
  failure at `ERROR` and writes the status line also with
  `FAILURE_ACTION=reboot` (#718).
- `OOB_EFI_VAR=true` stores the end of a run in the `BootyLastResult` UEFI
  variable when it changes, and the next run logs it (#718).
- The `METRICS_URL` summary has step data: duration, status (done, failed or
  skipped), retries, and the error and failure code of a failed step, for
  provision and deprovision runs. A deprovision run now posts the summary too
  (#706).
- Hardware watchdog: `WATCHDOG_ENABLE` arms `/dev/watchdog` (iTCO, AMD TCO,
  IPMI, ACPI WDAT, i6300esb) or, with `WATCHDOG_IPMI_FALLBACK`, the BMC
  watchdog, and pets it only while the provisioning step makes progress
  (step start, image bytes, disk commands) within its budget. A
  stuck step or a hung kernel resets the host (`BOOTY-WDT-001`). BOOTy
  disarms it at kexec, reboot and power off, or leaves it armed for the
  target OS with `WATCHDOG_HANDOFF=keep`. `WATCHDOG_TIMEOUT_SEC`,
  `WATCHDOG_DEVICE`, `WATCHDOG_STEP_BUDGETS`, YAML `watchdog.*`. See
  [hardware watchdog](docs/configuration.md#hardware-watchdog) (#721)
- GoBGP mode sends the BGP OPEN capabilities of FRR 10 with the bm4x template:
  graceful restart as helper (restart time 120 s), long-lived graceful restart
  and add-path receive. New keys `BGP_GRACEFUL_RESTART`,
  `BGP_GRACEFUL_RESTART_TIME`, `BGP_ADDPATH_RX`,
  `BGP_SOFTWARE_VERSION` (YAML `network.bgp.*`). In `BGP_PEER_MODE=dual` the
  numbered peers (route reflectors) get only L2VPN EVPN, like the template;
  before they also offered IPv4 unicast. The FRR 10.3 defaults that depend
  on `frr defaults` follow `BGP_DEFAULTS`, else the `frr.conf` profile,
  else `datacenter`: `bgp ebgp-requires-policy` (off with datacenter), the
  software version capability (every peer with datacenter) and zebra `ip
  nht resolve-via-default` (off with datacenter). The FQDN capability
  carries the system host name like FRR; the new key `BGP_HOSTNAME` (YAML
  `network.bgp.hostname`) sets it.
- BOOTy receives LLDP on every physical NIC, logs each new or changed
  neighbor and reports the current neighbors in the hardware inventory
  (`lldpNeighbors`). New key `LLDP_RECEIVE` (YAML `network.lldpReceive`, on by
  default); the legacy ramdisk only sends LLDP.
- New LLDP identity profile `LLDP_PROFILE=bm4x-cablecheck` (YAML
  `network.lldp.profile`): port ID = NIC MAC (subtype 3) and system name
  `bare-minimal`, the identity that the bm4x connection check matches. It sends
  on every physical NIC with carrier; `LLDP_EMIT_ALL` (YAML
  `network.lldp.emitAll`) also does that for the default `networkd` identity.
  `LLDP_PORT_ID_FORMAT` (YAML `network.lldp.portIDFormat`) selects its port
  ID: `mac` (default, subtype 3), `mac-string-colon` or `mac-string-dotted`
  (subtype 7 strings, for NX-OS leaves that show a MAC port ID as
  `aabb.ccdd.eeff`) or `ifname`. The default frames do not change.
- GoBGP mode applies the netplan device settings of the provision VXLAN device,
  the bridge and the NICs like systemd-networkd (MTU, MAC, learning, ARP proxy,
  hairpin, link-local, `accept-ra`), and `frr.conf` `[no] ip[v6] forwarding`.
  With the bm4x templates, `ip_forward` is now 0. New keys `VXLAN_MTU`,
  `VXLAN_MAC`, `VXLAN_LEARNING`, `VXLAN_ARP_PROXY`, `VXLAN_PORT_HAIRPIN`,
  `VXLAN_PORT_LEARNING`, `VXLAN_IPV6_LINK_LOCAL`, `VXLAN_ACCEPT_RA`,
  `BRIDGE_MTU`, `BRIDGE_IPV6_LINK_LOCAL`, `BRIDGE_ACCEPT_RA`, `BRIDGE_STP`,
  `ACCEPT_RA_OFF`, `IP_FORWARDING`, `IPV6_FORWARDING`. NICs with netplan
  `emit-lldp: true` (or `LLDP_EMIT`) send LLDP frames like networkd (#668). A
  set value of these keys wins over netplan. `NETWORK_DEVICES` (YAML
  `network.devices`, always strict) is the native form of the provisioner
  netplan and replaces the netplan files as a whole. Visible on CAPRF hosts
  with the bm4x templates, now like the legacy ramdisk: the VXLAN device has
  MTU 9000 instead of 9050, the VXLAN device and the bridge have no IPv6
  link-local address and `accept_ra` 0, the uplinks have `accept_ra` 0, the
  bridge STP follows `parameters: stp`, `ip_forward` is 0, and IPv6
  forwarding is now 0 by default in GoBGP mode (it was 1), so Neighbor
  Advertisements no longer carry the Router flag. The LLDP chassis ID is a
  machine ID per boot (locally assigned, 32 hex digits) like networkd; BOOTy
  creates it in `/run/booty/machine-id` and never uses or writes
  `/etc/machine-id`.
- GoBGP mode applies the `frr.conf` route-maps and community-lists, explicit
  and automatic EVPN route targets, and the `local-as` AS path loop check. New
  keys `BGP_ROUTE_MAPS`, `BGP_COMMUNITY_LISTS`, `BGP_ROUTE_MAP_IN`,
  `BGP_ROUTE_MAP_OUT`, `EVPN_RT_IMPORT`, `EVPN_RT_EXPORT` (#659). Native
  sessions take per-family `routeMaps`; native route-map and community-list
  lists replace the `frr.conf` lists as a whole, and the native JSON vars
  lists reject unknown fields. `bgp ebgp-requires-policy` is applied like
  current FRR (on unless `no bgp ebgp-requires-policy`; new key
  `BGP_EBGP_REQUIRES_POLICY`, YAML `network.bgp.ebgpRequiresPolicy`).
  With `frr defaults traditional` (`BGP_DEFAULTS=traditional`), native eBGP
  sessions (`BGP_SESSIONS`) without route-maps exchange no routes: give them
  `routeMaps` or set `BGP_EBGP_REQUIRES_POLICY=false`. The
  rejected families are logged at WARN. The `frr.conf` route targets now win
  over `vpn_rt`, as in FRR (#659).
- GoBGP mode runs BFD (RFC 5880, 5881, 5883) for `frr.conf` neighbors with
  `bfd`, with the profile timers, and drops the BGP session when BFD goes down.
  New keys `BFD_DETECT_MULTIPLIER` and `BFD_PROFILES` (YAML
  `network.bgp.bfdProfiles`, the native `bfd` / `profile` blocks) (#655).
- Native vars keys and YAML fields for every provisioner network value of GoBGP
  mode (`BGP_LOCAL_AS`, `BGP_NEIGHBOR_VRF`, `BGP_CONNECT_RETRY`, `BGP_ALLOWAS_IN`,
  `BGP_INSTALL_ROUTES`,
  `BRIDGE_MAC`, `VXLAN_LINK`, `UNDERLAY_DUMMY_NAME`, `MTU`, `OVERLAY_VRF_NAME`,
  `OVERLAY_VRF_TABLE_ID`). A set value wins over netplan and `frr.conf`; the
  four peer keys are defaults for the sessions that do not set the value
  (#654).
- GoBGP mode installs and originates IPv6 EVPN Type-5 routes like zebra (via the
  IPv4-mapped VTEP), applies netplan `lo` addresses and `frr.conf` blackhole
  routes, and uses Type-5 only for an L3VNI provision VNI. `EVPN_TYPE5_ONLY` can
  now be set to `false` explicitly. New keys `LOOPBACK_ADDRESSES`,
  `BLACKHOLE_ROUTES`, `EVPN_TYPE5_NETWORKS`, `BRIDGE_NAME`, `VXLAN_NAME`; a set
  value wins over netplan and `frr.conf`, a list replaces the parsed list (#651).
- GoBGP mode installs the learned unicast routes into the session VRF table like
  zebra, and stops an uplink session when its NIC loses carrier (#645).
  `allowas-in` and `bgp bestpath as-path multipath-relax` are applied, also
  natively (`allowASIn` per session, `network.bgp.multipathRelax`,
  `BGP_MULTIPATH_RELAX`). `[no] bgp fast-external-failover` is parsed and
  native (`BGP_FAST_EXTERNAL_FAILOVER`, YAML `network.bgp.fastExternalFailover`).
  Routes go to the table of each session's VRF with metric 20, recursive next
  hops are resolved like zebra, and the multipath rule follows FRR 10.3.
- GoBGP mode opens one BGP session per `frr.conf` neighbor with its own
  attributes (peer-groups, `remote-as internal`, `local-as`, timers, address
  families, VRF), also on FRR uplinks that netplan does not list. The same
  sessions can be set natively with `network.bgp.sessions`, `peerGroups` and
  `defaults` (`BGP_SESSIONS`, `BGP_PEER_GROUPS`, `BGP_DEFAULTS`) (#643).
- `MODE=decommission`: wipe all disks (best effort), remove every EFI
  `BootOrder` entry, report success (#586)

  the preset mechanism (#648)
- `DISK_SELECTION` (`prefer-nvme`|`lsblk`), `WIPE_ALL_DISKS`, `DISCARD_NVME` (#649)
- `SKIP_TLS_VERIFY`, `EXPORT_VARS` (#650)
- `PROVISIONER_FILES_TARGET` (`target`|`ramdisk`), `WRITE_RESOLV_CONF`,
  `RAMDISK_HOSTNAME` (#652)
- `GRUB_CMDLINE_MODE` (`resolved`|`append`) (#653)
- `NIC_FIRMWARE_LOG`, `NUM_VFS_MODE` (`set`|`raise`) (#656)
- `GROW_PARTITION` (`root`|`last-linux`) (#657)
- `NETWORK_WAIT_MODE` (`default`|`rounds`); `NETWORK_WAIT_MAX_ATTEMPTS` now

- `MACHINE_COMMANDS_MODE` (`command`|`script`) (#675)

  recommends `DISK_SERIAL_NUMBER` (#666)
- Standby: the payload of a `provision` or `deprovision` command (vars lines)
  wins over `/deploy/vars` for that command; unknown keys, settings of the
  running ramdisk and bearer-token URLs are rejected. `STANDBY_DEPROVISION_SUCCESS_ACTION=standby` returns to standby
  after a deprovision command in the same boot. Agent paths `/agent/...`
  documented (#665)
- Standby: the `completed` ACK of a deprovision command names the disks in
  use that the wipe of all disks skipped, like the success status (#679)
- Standby: a `provision` or `deprovision` command payload can be a deploy
  archive (#730), the gzip tar of the per-job `deploy/` tree that CAPRF
  renders for an ISO (vars, cloud-init seed, machine files and commands,
  provisioner files). BOOTy stages and checks it, swaps the directories into
  `/deploy` right before the command runs, keeps the file permission bits
  (no setuid, setgid or sticky), ignores unknown vars keys like the ISO, and
  keeps the agent token, network and `CAPRF_LEGACY_COMPAT` of the running
  ramdisk. With `PROVISIONER_FILES_TARGET=ramdisk` the new provisioner files
  go into the ramdisk before the command runs, without `etc/frr` and
  `etc/netplan`. Symlinks, hard links, paths outside `deploy/`, `..`
  anywhere in an entry name (also `a..b`), vars without a known key and
  oversized archives fail the command; a failed command drops its staged
  files.
- Standby picks up commands faster (#716): the command poll is a long poll
  (`GET COMMANDS_URL?wait=20`; CAPRF holds it until a command is queued, at
  most 25 s), the next poll starts 10 s after the start of the previous one
  (also after a failed poll, at once when the poll took longer), and after a
  poll that returned commands after 1 s or the rest of the 10 s, whichever is
  shorter. Heartbeats run in their own goroutine, so a long poll does not
  delay them; they pause while a command runs. The disk settle wait is skipped when the set
  of block devices did not change since the last settle in the same boot, the
  2 s pause before the handoff (kexec, reboot, power off) is removed, and the
  standby start logs `memTotalMiB` and `memAvailableMiB`.
- Token renewal and expiry: `TOKEN_RENEW_MARGIN_SECONDS`,
  `TOKEN_RENEW_RETRIES` and `TOKEN_RENEW_BACKOFF_SECONDS` control the

  of a token without renewal. When the token can not be renewed or expires, BOOTy stops the
  active task, reports the reason to `ERROR_URL` and ends like a failed run
  (#680)

  second disk with a `<label>-disk2` UEFI boot entry, installs GRUB on both
  disks on BIOS, and installs the `booty-esp-sync` service that copies later
  ESP changes to the other disk. Soft deprovision refuses a mirrored root (#581)

- The hardware inventory reports SR-IOV per PF port from sysfs, devlink and
  rtnetlink, without vendor tools: driver, firmware, PCI address and IDs,
  NUMA node, link type, `sriov_totalvfs` and `sriov_numvfs`, the devlink

  check, VLAN, QoS, rates, MAC, link state) with strict validation. The new

- `configure-sriov` applies the runtime settings of the SR-IOV profiles in
  the ramdisk through generic kernel interfaces (`sriov_numvfs` in sysfs, the
  devlink eSwitch mode, the rtnetlink VF attributes), checks them, and

- The SR-IOV in-use guard refuses VF count changes on a port the ramdisk
  network uses only for drivers that reset the PF for them (igb, ixgbe,

### Security

- disk: wipes, discards and secure erase do not touch a disk that backs a
  mounted file system or an active swap area, also through LVM, dm-crypt or
  MD. A wipe of all disks skips such a disk and goes on (the success status
  names it); a selected target disk fails the run, and so does a failed check
  (#667)
- qcow2 images with a backing file or an external data file are rejected before
  the conversion to raw (#609)
- CAPRF transport errors carry only scheme, host, path and a fixed cause (#624)
- The FRR connectivity wait redacts the target URL; each `vtysh` dump has a 10 s
  timeout (#627)
- Machine-files symlinks are recreated, never followed (#629)
- `SKIP_TLS_VERIFY` never applies to `TOKEN_URL` or the crash upload (#589, #650)
- `pkg/tpm` attestation (library only; provisioning does not use it yet): the
  AK is a restricted ECDSA P-256 signing key of the endorsement hierarchy,
  `MakeCredential` and `ActivateCredential` bind it to the EK, and
  `VerifyQuote` checks a quote against a trusted AK, the nonce and the signed
  PCR digest. `VerifyQuoteSignature`, which used the key carried in the
  quote, and the `PubKeyX`, `PubKeyY` and `PCRDigest` quote fields are
  removed. BOOTy PCR events move from PCR 8, 9, 10, 14 and 15 (GRUB, IMA,
  shim, systemd) to PCR 23 (`PCRBooty`); the cryptenroll proposal no longer
  binds PCR 14 (#707)

- Unsupported GoBGP underlay/BFD combinations, IPv6 GoBGP neighbors, ambiguous root partitions, missing secure erase tools and missing system-A/B data mountpoints fail closed (#320, #341, #345, #386, #414, #430)
- The unused Go packages `pkg/bios`, `pkg/bootloader` and `pkg/event` were removed (#463, #474)
